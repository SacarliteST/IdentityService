# AGENTS.md

Инструкции для AI-агентов и разработчиков, вносящих изменения в IdentityService.

## Назначение проекта

IdentityService отвечает за:

- регистрацию и аутентификацию пользователей;
- выпуск, ротацию и отзыв JWT/refresh-токенов;
- роли `Admin`, `Teacher`, `Student`;
- административное управление пользователями;
- блокировку учётных записей;
- аудит входов и административных операций;
- публикацию OpenID discovery и JWKS для других сервисов Scoodle.

Сервис будет использоваться несколькими модулями платформы. Изменения JWT, issuer, audience, claims, ролей и JWKS считаются межсервисными контрактными изменениями.

## Перед началом работы

1. Прочитайте `README.md`, `CONCEPT.md` и `ROADMAP.md`, если файлы доступны.
2. Проверьте `git status` и не изменяйте чужие незакоммиченные файлы.
3. Изучите существующий вертикальный срез с похожим поведением.
4. Сверьте HTTP-контракты в `Contracts` и маршруты в `Contracts/ApiRoutes.cs`.
5. Не запускайте Host, если задачу можно проверить через интеграционные тесты.

## Архитектура

Соблюдайте текущие границы проектов:

- `Host` — composition root, конфигурация и запуск;
- `Web` — Minimal API, CQRS-срезы, валидация, авторизация и токены;
- `Domain` — доменные сущности и их инварианты;
- `Data` — EF Core, конфигурации сущностей, миграции и сидинг;
- `Contracts` — публичные DTO, enum, константы и маршруты;
- `Client` — типизированный HTTP-клиент;
- `Common` — общие CQRS/result-примитивы;
- `Tests/IntegrationTests` — интеграционная проверка поведения API.

Новая пользовательская операция в `Web` оформляется вертикальным срезом:

```text
Web/Features/<Area>/<Feature>/
  <Feature>Endpoint.cs
  <Feature>Command.cs или <Feature>Query.cs
  <Feature>Handler.cs
  <Feature>Validator.cs, если есть входные данные
```

Handler регистрируется в модуле своей области. Endpoint обнаруживается автоматически через `IEndpoint`.

## HTTP API

- Используйте Minimal API и существующий `IEndpoint`.
- Маршруты объявляйте в `Contracts/ApiRoutes.cs`.
- Публичные request/response-модели размещайте в `Contracts`.
- Для изменяющих административных операций требуйте роль `Admin`.
- Явно описывайте `Produces`, `ProducesProblem` и `ProducesValidationProblem`.
- Ошибки валидации возвращайте как `ValidationProblemDetails` со статусом `422`.
- Используйте `Result` и `Result<T>` для ожидаемых ошибок, не исключения.
- Для неизвестного ресурса возвращайте `404`, для конфликта состояния — `409`.
- Сохраняйте стабильную сортировку постраничных выборок.
- Не возвращайте пароли, password hash, raw refresh-токены, private keys и другие секреты.

При добавлении или изменении публичного endpoint обновляйте:

1. `Contracts`;
2. handler и endpoint;
3. типизированный `Client`;
4. runtime OpenAPI contract test;
5. интеграционные тесты.

Не изменяйте корневой `swagger.json` автоматически. Владелец проекта обновляет этот файл вручную.

## Identity и безопасность

- Роли задаются через `UserRole`; свободные строковые роли не принимайте.
- Полный набор ролей заменяется атомарно через `PUT /api/v1/users/{id}/roles`.
- Нельзя снять у себя роль `Admin`.
- Нельзя удалить доступ у последнего активного администратора.
- Нельзя заблокировать собственную учётную запись.
- При блокировке отзывайте активные refresh-токены.
- Login и refresh заблокированного пользователя должны отклоняться.
- Access JWT остаётся автономным и действует до `exp`; не добавляйте обращение к Identity DB в другие сервисы для каждой проверки токена без отдельного архитектурного решения.
- Не меняйте набор claims, issuer, audience, алгоритм подписи или JWKS без оценки влияния на все сервисы-потребители.
- В БД храните только хэш refresh-токена.
- Не записывайте токены, пароли и ключи в логи или аудит.

## Транзакции и аудит

Операции, состоящие из нескольких записей, должны быть атомарными. Используйте транзакцию того же `AppDbContext`, который используется `UserManager`.

Аудит должен коммититься вместе с бизнес-операцией. Сейчас аудитируются:

- успешный login;
- административное создание пользователя;
- замена ролей;
- блокировка;
- разблокировка.

Не создавайте событие для неуспешной операции. Описание события должно быть безопасным и не содержать request body целиком.

## Entity Framework Core

- Добавляйте сущность в `Domain` и `DbSet` в `AppDbContext`.
- Конфигурацию размещайте в `Data/Configurations`.
- Для изменения схемы создавайте новую миграцию и обновляйте model snapshot.
- Не переписывайте миграции, которые могли быть применены в общем окружении.
- Индексы добавляйте под реальные фильтры и сортировку.
- Read-only запросы выполняйте с `AsNoTracking()`.
- Избегайте N+1-запросов.
- Не меняйте существующую структуру БД вне границ задачи.

## Тесты

Интеграционные тесты обязаны использовать PostgreSQL Testcontainers. Запрещено запускать их на `identity_db` или другой обычной локальной/production базе.

- Test host получает строку подключения только от `PostgreSqlContainer`.
- Миграции применяются к контейнерной базе.
- Контейнер должен освобождаться после набора тестов.
- Docker Desktop должен быть доступен; тесты не должны тихо переключаться на реальную БД.

Покрывайте интеграционными тестами:

- успешный сценарий;
- `401` без токена;
- `403` без нужной роли;
- валидацию и граничные значения;
- `404` и конфликты;
- атомарность составных операций;
- защитные правила администратора;
- отсутствие секретов в ответах и аудите.

Работайте экономно: сначала завершите весь этап и добавьте тесты, затем выполните единый итоговый прогон. Не запускайте полный набор после каждой мелкой правки. Если итоговый прогон обнаружил ошибку, исправьте её и повторите полный прогон.

Итоговые команды:

```powershell
dotnet format IdentityService.sln --no-restore
dotnet build IdentityService.sln --no-restore
dotnet test IdentityService.sln --no-build --no-restore
```

Сборка должна завершаться без предупреждений: в проекте включён `TreatWarningsAsErrors`.

## Локальный Host

Если для проверки необходимо вручную поднять сервис:

1. используйте `http://localhost:5101` или свободный альтернативный порт;
2. дождитесь успешного ответа нужного endpoint;
3. завершите только процесс, который запустили сами;
4. никогда не оставляйте IdentityService работать после проверки;
5. не завершайте процесс, запущенный пользователем из Rider.

Для обычной проверки API предпочитайте `WebApplicationFactory` и Testcontainers.

## Стиль кода

- Следуйте существующему C#-стилю и nullable annotations.
- Используйте file-scoped namespace в новых файлах.
- Предпочитайте понятный явный код переусложнённым generic/helper-абстракциям.
- Добавляйте абстракцию только при реальном повторении или сложной ответственности.
- Не смешивайте функциональную доработку с несвязанным рефакторингом.
- Комментарии оставляйте только там, где они объясняют причину или инвариант.
- Не подавляйте предупреждения без обоснования.
- Не добавляйте новые пакеты, если задача решается текущим стеком.

## Git

- Не отменяйте и не включайте в коммит чужие локальные изменения.
- Перед коммитом проверяйте `git diff --check` и staged-состав.
- Коммиты делайте на русском языке.
- Один завершённый этап оформляйте отдельным логичным коммитом.
- Не коммитьте секреты, ключи подписи, локальные файлы IDE и содержимое временных контейнеров.
- Не выполняйте destructive-команды (`git reset --hard`, удаление чужих изменений) без явного запроса владельца.

После работы кратко сообщите:

- что реализовано;
- результат сборки и количество тестов;
- hash и название коммита, если он создан;
- остались ли незакоммиченные изменения;
- остановлены ли запущенные агентом процессы и контейнеры.
